# Web build

The `web` module uses the gdx-teavm fork in `vendor/gdx-teavm` and the TeaVM
fork in `vendor/teavm`, both through Gradle composite builds.
The submodule gitlink pins the compiler revision. `settings.gradle` substitutes
TeaVM Maven coordinates with included-build projects, including the Gradle
plugin and class library. Publishing TeaVM to Maven is not required.

## Build

Initialize the pinned compiler source after cloning:

```sh
git submodule update --init --recursive
```

Build the JavaScript target from the game repository:

```sh
./gradlew :web:gdx_teavm_web_js_build
```

The generated site is `web/build/dist/js/webapp` (debug output is
`web/build/dist/js/debug/webapp`). Serve the distribution directory over HTTP:

```sh
python3 -m http.server 8080 --bind 127.0.0.1 --directory web/build/dist
```

Open `http://127.0.0.1:8080/js/webapp/`. Loading the HTML through `file://` is not
supported by the browser asset loader.

The composite build was verified with the game's Gradle 9.5 wrapper and JDK 25.
TeaVM manages its build-time Node dependency; if Node is already installed,
`-Pteavm.localNodeJS=true` can use it instead. No global toolchain changes are
required.

## Compatibility

Monitor timeout/interruption, listener cleanup, entry-queue handoff, and
compression fixes come from the minimal pinned fork. Random sequences, float
precision, and number formatting retain upstream TeaVM 0.16.0 behavior.
The optional number-symbol override was removed; locale data retains TeaVM
behavior. The gdx-teavm fork supplies platform-loader fields, static nested-class
metadata, and WebGL client-array support without game class-name assumptions.

Reflection metadata, browser input, rendering, fonts, audio, and game-loop
scheduling live in `web`. The shared `core` and `SPD-classes` sources are
consumed without Web-specific edits. Saves use the backend's browser storage.
The launch page is generated by the backend during the build.

## Updating TeaVM

Check out the intended commit in `vendor/teavm`, build and verify the game, then
record the new gitlink in the game repository when ready. Updating the fork's
`master` alone does not change the compiler used by an existing game checkout.

## Integration validation

The reduced fork passed 18 Object/DeflateStream test methods on optimized and
unoptimized JavaScript, plus core/classlib main and test checkstyle checks.
The release JS build, new-game movement, saving, and reload/continue were
verified with the reduced fork. Full-playthrough validation remains pending.

The pinned TeaVM revision includes the monitor entry-queue fix.

Run compiler tests from `vendor/teavm` using its own wrapper. Invoking its test
task through the outer Gradle 9.5 composite hit an unsafe-configuration-resolution
check; this does not affect the game generation tasks.

## gdx-teavm fork

The fork starts from upstream 1.6.2 to match the published Gradle plugin. The
plugin remains a Maven dependency; runtime and shared backend artifacts are
substituted by `includeBuild`. The gdx-teavm fixes are committed and pushed to the fork master. The game
gitlink pins the verified backend revision. JVM and compiled-JS regression tests live in
`backends/backend-web/src/test` in the fork.
